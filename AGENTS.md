## MTB-APP

Clinical-trials platform: Expo/React Native frontend (`frontend/`) + FastAPI/MongoDB backend (`backend/`). Setup and run instructions are in `README.md`. Two scheduling systems coexist by design — see Where things are.

## Policy

- Never enable `DEV_OTP_MODE` outside local dev — it accepts a fixed OTP for any unconfigured channel, leaving signup open. (`backend/server.py:1318`)
- Never flip `UCTSM_AUTHORITATIVE` (off by default, `backend/.env.example:111`) without confirming per-trial parity first — it activates a middleware (`server.py:10380–10400`) that returns HTTP 410 on every legacy schedule-authoring route, and both code paths are live simultaneously today.
- Never migrate `sponsor/visit-schedule.tsx`, `clinical/schedule-review.tsx`, or `clinical/trial-summary.tsx` to read from the UCTSM engine without checking `MTB_IMPLEMENTATION_HANDOFF.txt` (section C3/D-4) first — they carry legacy visit-comment/task/edit features the engine has no equivalent for. Zero UCTSM imports in any of the three today.

## Where things are

- Authoritative store per concept: Trial, Protocol/schedule-definition, Patient, and visit **writes** are Mongo only (`backend/server.py`); visit **reads** follow `Trial.schedule_read_mode`, defaulting to `LEGACY` and changeable only through the gated `ParityService.set_read_mode` (`app/services/parity_service.py:206`), which refuses `ENGINE` unless every enrolled patient's dates already match — no trial has been moved yet. Condition state exists *only* in Postgres (`uctsm_patient_conditions`, no Mongo equivalent). The audit trail is two unreconciled logs — Mongo `audit_logs` vs. Postgres `uctsm_audit_events` — neither writes the other.
- Protocol extraction has no engine right now (both previous pipelines were deleted 2026-09-23; the pre-deletion snapshot is commit `0dd7c67`, pushed to `testing/universal-schedule-engine`). Upload endpoints (`/protocols/extract`, `/protocols/extract-details`, `/trials/{id}/extract-schedule`) validate the file then return 503 via `raise_extraction_unavailable()` in `server.py`; UCTSM runs fail immediately. The new engine plugs into `extract_schedules` in `backend/app/extraction/runner.py`, consuming `DocumentPage`s and returning `ExtractionResult`s (`app/extraction/contracts.py`). `protocol_extraction.py` now holds only the legacy `ExtractedSchedule` model and its deterministic expansion — no model calls. The curated gate in `MTB_IMPLEMENTATION_HANDOFF.txt` section E still lists the deleted `test_uctsm_extraction.py` and `test_uctsm_footnote_completeness.py`; drop them when running it.
- Add Trial (`sponsor/add-trial.tsx`, rebuilt 2026-10-24) is a kit-only 5-step flow: protocol ID lookup (upload popup if not on record) → analysis → questions (`KitQuestionsModal`) → trial details → schedule check and save. It no longer consumes UCTSM extractions or builds a canonical schedule. The schedule step and `sponsor/kit-schedule.tsx` render `ProtocolTimeline`; its sections come from each visit's AI-written `phase`, grouped by `src/features/kit/sections.ts` (only case/space/hyphen differences merge; section renames are saved into the base model's visit phases).
- Patients are scheduled by the kit engine only (2026-10-23): `clinical/add-patient.tsx` reads the trial's reviewed model (`GET /trials/{id}/kit-model`), asks the start date, the protocol dates at or before Day 1 and participant questions, and sends the record as `kit` on `/patients/invite`; a trial without a saved kit model cannot enrol. The patient doc stores only that record (`patients.kit`, validated by `clean_participant` in `kit_routes.py`) — no `visit_instances` are created; every screen computes dates client-side with `computeKitSchedule` (staff: `clinical/kit-patient.tsx` → `KitPatientView`, `PUT /patients/{id}/kit`; patient: `/me/kit` via `fetchMyVisits()`). Patient schedules render as `PatientTimeline`; `patientSections.ts` derives late/moved visits (against a no-actuals baseline), event-cancelled visits (against a no-events run, shown as one row at the causing event) and dates still to enter. Server-side visit reminders and anything else reading `visit_instances` do not see kit patients.
- "If this happens" schedule changes live in the kit model's `rules` (2026-10-24): each has a trigger (`when`: an anchor's date or a logged event), `stop_visits`/`stop_all`, `same_day`, `starts`, `blocks`, `allowed` (when the trigger may happen — validation only, it never picks a branch) plus `effect`, `source` and `if` (2026-10-26: conditions that must all hold — a participant/decision answer, an answer logged with the event, the trigger's timing against an anchor or visit, or the nth occurrence; branches of one event are separate rules told apart by `if`, and `normalize.norm_rule_if` drops a rule whose condition is unusable rather than keep it unconditional). The AI writes them (`_prompt_text.py`) and the cross-check adds ones it finds in table footnotes (`rules_add`); `normalize.norm_rules` drops unknown references. `schedule.ts` applies a rule only once its date is known (visits it would stop carry `stopsIf` until then), returns `stoppedBy` and `warnings`; an ending event keeps visits counted from the anchor it sets. Models saved before this have no rules — re-run the analysis to get them. Engine tests: `npm run test:kit` (`tests/kit-rules.test.ts`).
- Kit upload reads schedule tables by structure, never by matching words (2026-10-26): ruled tables come from `find_tables()` cells when one short mark repeats across rows and columns (`pdf_input.schedule_tables`, sent as `|` grids with `←`/`↑` for merged cells); tables laid out with spacing only come from lined-up standalone marks (`pdf_input.aligned_table`) and are transcribed by the model from the page image in `app/kit/tables.py`, checked against per-row/per-column mark counts with up to 2 rechecks — rows still off become a `table_check_p<N>` review question. Unreadable symbols become `[S#]` tags plus a symbol-legend image (`SymbolLegend`); Wingdings/Symbol private-use characters are translated directly. The first model call also returns `schedule_table_pages` (popped before saving), which the cross-check adds to the detected pages. Backend tests: `tests/test_kit_pipeline.py`, `tests/test_kit_tables_route.py`.
- Kit schema additions (2026-10-28, `prompts.py` extends the untouched `_prompt_text.py`; checked in `normalize.py`, applied in `schedule.ts`, tests `tests/test_kit_schema_extensions.py` / `frontend/tests/kit-schema-extensions.test.ts`): anchor `range` (a date with a range becomes an entered `ask` date, its gap kept only as an estimate; outside the range is warned, never refused), repeat `stages`/`max_days`/`max_delay_days`/`delay_effect`, every-nth `overrides` (`every`/`from`/`to`), visit `min_gap`/`prep`, procedure `need`/`reuse_within_days`, conditions with `op`/`any`/`not`, rule `set_answers` (crossover) and `pause` (shift/skip until a resume anchor). A repeat with no stated count is never 1: it shows 6 ahead with a note. Reviewer load is kept low by `normalize._prune_review`: questions that only pick a date gap become a range, open-ended preview counts and no-effect questions are dropped (noted in `notes`); `table_check_*` always stays. Add Patient asks only protocol dates at or before Day 1 (`participant.enrolmentAnchors`); later ones are added on the patient's schedule. Conditions can also test what happened by a visit's date (`{event, happened}`, `{visit, n, status: done|missed|not_done}`; missed uses `participant.today` or the device date; not allowed in rule `if`). Model versions: `PUT /trials/{id}/kit-model` keeps the replaced doc in `trial_kit_model_history` and stores `version`, `file_sha256`, `analysis_warnings`, `corrections`; patients (and pending invitations) are pinned to their `kit_model_version` and never move on a re-save — the save response lists who could move, `GET /patients/{id}/kit` returns their version plus `latest` (with the blocking problem, if any), and `POST /patients/{id}/kit/move-to-latest` (pi/crc) moves one after `clean_participant` passes. The protocol file is kept with its analysis job and stored in GridFS bucket `kit_protocol_files` (by sha256) only when the model is saved with that `analysisJobId`; download via `GET /trials/{id}/kit-model/file?version=`. Patients open kit visits in `patient/visit-detail.tsx` through `fetchMyKitVisit` (keys contain `#`), with preparation, notes and assessments.
- Events check (2026-10-28, `app/kit/events.py`, stage `events` after `verify`): a third model request reads the whole protocol (split in parts on `prompt_too_large`; skipped with a note for scanned PDFs) for what logging each event changes. It must answer for every model event plus a fixed `CHECKLIST` (pregnancy, withdrawal, early stop, death, lost to follow-up, SAE, dose hold/change, progression, overdose, rescue, unscheduled, screen failure) with status `changes`/`no_schedule_change`/`not_in_protocol` and verbatim page quotes, which are looked up word by word in `pageTexts` (unfound quotes become notes). Merged additively: event visits/rules matched by id (visits also by code), removed only via `remove_visits`/`remove_rules` with a reason; `add_tests` become procedures with `if: [{event, happened: true}]`, `remove_tests` add `{not: {event, happened: true}}`; `anchors_add` are always `ask`. Stored as `event.check`, `event.site_actions` (actions that are not visits) and model `event_check` (`eventCheck` in the analysis result). Gaps (unreported events, unanswered checklist items, conflicts with the model) go to `notes`; no UI shows the check yet. Tests: `tests/test_kit_events.py`, `frontend/tests/kit-event-check.test.ts`.
- Cropped PDF pages (2026-10-28): every kit PDF open goes through `pdf_input.uncrop_pages` / `open_pdf`, which resets each page's crop box to its media box before text, tables or images are read (NCT00318643 hid its schedule-table footnotes, incl. the ±3-day visit window, outside the crop). Pages where the crop hid ≥200 characters or ≥20% of a picture are returned as `hiddenPages`, become an analysis warning/note and show in the `read` stage detail; a cut-off running header is read but not reported. Tests: `test_a_cropped_page_is_read_whole_and_reported` in `tests/test_kit_pipeline.py`.
- Visit checks, measured values and dose levels (checks 2026-10-29; values/doses 2026-10-30): a visit `check` is a yes/no asked at every occurrence ("No" holds it until a "Yes"; `max_wait_days` + `on_timeout: "stop"` stops visits). Model top-level `measures` (value or CTCAE grade, `worse` direction) and `doses` (levels highest first, `start` null when unstated, `below_lowest` stop|warn) are present only when the protocol has them. A check's `limits` (`value`, `baseline_factor`, `of` latest/worst_here/worst_so_far, `any`) work the Yes/No out from entered values; a limit that can't be worked out (no baseline yet) falls back to a staff Yes/No, and a limit normalize can't read drops ALL the check's limits. `dose_changes` on a check (need an `if`; may use `held_days`, `occurrence`/`and_later`) or on a rule (doses after its date) step/set/stop a drug's level; levels run through the drug's doses in date order (`schedule.ts` 3b), going below the lowest level stops visits only with `below_lowest: "stop"` or `stop`. Record: check entries `{date, answer?, values?}`, `baselines`, `doseLevels` (staff-set, validated in `clean_participant`). Checks on event-triggered visits are not run (normalize drops them with a note). Event-added visits (keys `ev.<logged event key>.<visit id>#n`, accepted by `clean_participant`): repeats count from the event date unless `repeat.chain` (the protocol counts from the previous visit), then from the previous one's recorded date; a rule's `stop_visits` may name them (normalize `stop_ids`), and they carry `stopsIf` (`tests/kit-event-visits.test.ts`). "30 days after the last dose" (2026-10-30): anchor `kind: "last_visit"` with `last_of` (scheduled visits) = the latest of them still on the schedule (recorded or planned; unknown while one has no date; never entered by staff), computed in the visit loop once those visits are done (`schedule.ts` `setLast`); events and `stop_all` rules carry `keeps_visits` (only when non-empty), visits that still happen when they end the schedule — so withdrawal after Period I keeps the call, dated from the Period I dose (`tests/kit-last-dose.test.ts`). With `stop_is_last_dose` (drug taken daily between visits, e.g. APD334-202) the date of a fired `stop_all` rule is the last dose instead, so follow-up counts from a stop logged between visits (2026-10-30). Event-visit `include_if` may use `event_question` (an answer given with the event); before 2026-10-30 such visits were always added. "Check in at least 12 h before dosing": visit `arrive_before: {visit, hours}` (kept only when valid); staff record the check-in time on that visit in `participant.doseTimes` (the same HH:MM field the dose time uses, entered on the visit sheet; rows carry `time` and `timeKind` "checkin"|"dose"), the dose visit with the same occurrence number shows "Dose from HH:MM" and a dose time entered earlier is a warning (`schedule.ts` 3a, `tests/kit-checkin-time.test.ts`). That field also turns on the PK timepoint clock times, which had no input before. Assessments limited by criteria found during the study ("stool O&P if eosinophils >2 × ULN and a risk factor") are decision questions asked at that visit (number or yes/no) gating the procedure's `if`; `if_indicated` is only for investigator judgment. Decision rows carry `kind`; number decisions are answered through an "Enter value" input (`NumberAnswer` in `KitPatientView`) — before this they had no input (`tests/kit-screening-decisions.test.ts`). Tests: `tests/test_kit_measures_doses.py`, `frontend/tests/kit-visit-checks.test.ts`, `kit-measures-doses.test.ts`.

See `docs/p6-completion-record.md`.

## Running and verifying

- Backend: don't run plain `pytest` across the whole suite — several TestClient-based integration modules (e.g. `test_schedule_edit.py`, `test_schedule_definition_api.py`, `test_protocol_creation.py`) error on teardown when run together in one session (an anyio/starlette event-loop issue), though each passes alone. Use the curated 34-file gate listed in `MTB_IMPLEMENTATION_HANDOFF.txt` section E.
- Frontend: there is no plain `npm test`; use `npm run test:uctsm` or a single `test:uctsm-*` script.
- `npm run lint` cannot run in this environment — Expo shells out to `yarnpkg`, which isn't installed here.
- `npx tsc --noEmit` over the whole frontend project runs out of memory on this machine, and no scoped tsconfig exists to work around it — typecheck only the files you touched instead (e.g. `npx tsc --noEmit <files>`).

## Known pitfalls

- Don't default or guess an unstated value (visit mode, dependency mode, recurrence maximum, footnote scope, etc.) — mark it UNRESOLVED / AWAITING_ANCHOR / blocked-pending-review instead. Repeated historical fixes exist because this was violated (e.g. commits `e2b812e`, `bfad44c`, `94084d0`).
- Don't trust a status doc's claim about what's committed — check `git status`/`git log` yourself. (An architecture audit dated the same week claimed 370 uncommitted lines in `schedule_schema.py`; all of it was committed by the next session.)
- Two independent reminder systems share no code: patient medication alarms (`db.reminders`) vs. the engine that bridges UCTSM projections into visit-reminder notifications (`server.py:8695–8714` vs. `5544–5633`).
- Push-token registration (`POST /push/register`) exists but nothing sends an actual push (no FCM/APNs/Expo integration), and the frontend never registers a token either — don't assume push notifications work end-to-end.
- "Messages" refers to two unrelated systems — 1:1/group WebSocket chat and an admin one-way broadcast with its own scheduler worker — check which one a task means.
- Trial/team invites, admin-issued platform invitations, and org-admin member invites are three independent handlers with separate token schemes and no shared code — a fix to one doesn't apply to the others.
- `POST /auth/register` (single-call) and the OTP wizard (`/auth/register/start → verify → complete`) are both live; only the OTP wizard is what the app actually uses.

## Prompt delivery - user preference

- Save every new full implementation or continuation prompt prepared for the user as a descriptive `.md` file under `docs/` before sharing it.
- Link the saved file in the response and maintain `docs/claude-code-prompts-index.md`; update `docs/claude-code-next-prompt.md` when the next action changes.
- Preserve historical prompt files and clearly identify the current prompt and superseded instructions. Saving a prompt does not authorize deployment, clinical policy changes or data migration.
