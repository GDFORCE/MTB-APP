# Scheduling ownership and dependency boundaries

Verified scope: the current continuation tree on 19 October 2026. This describes implemented boundaries and remaining mixed responsibilities. It does not claim that the whole application has migrated to a single scheduling system.

## Authorities that still coexist

The operational Mongo collections written by `server.py`, the SQL UCTSM services, and the explicitly configured canonical Mongo plane remain distinct. Native command/amendment patients live in the canonical plane with persisted authority. Existing SQL-only patients are not silently mirrored. A matching event code, patient label or UUID-looking string is not evidence that records belong together. Per-trial parity/read-mode gates and the existing operational relationship provider remain required. This continuation changes no real cohort, global authority flag or read mode.

| Canonical rules and evaluation | `domain/schedule`: portable typed UUID/value models, validator, graph analysis, temporal rules, tracks, recurrence, manual handling, amendment mapping and pure evaluator | No database, API, provider or UI imports. Worker attempt tokens and leases fence completion/failure/renewal. The retained SQL runner is compatibility code, not a second Mongo store. The port runner still needs a complete production upload/queue entry point. |

## Import rules and compatibility

Domain imports domain/value libraries. Application imports domain and portable ports/contracts; it must not import `app.services`, `app.api`, `app.db`, database drivers or API frameworks. Persistence implements ports and performs representation conversion. HTTP/job adapters translate identity, authorization, requests and responses into application calls. No new scheduling business logic belongs in `server.py`.

The pure review builder moved from `services/review_view` to `application/review_projection`; SQL mutation workflow remains in the service facade. Pure schedule/operational projection modules and the canonical ingestion adapter have equivalent compatibility facades. Existing imports retain their object identities. Shared HTTP identity and maker-checker error adapters live in `api/uctsm_shared`; Mongo route modules no longer import the SQL router merely for helpers. These are characterized vertical slices, not permission to delete all old services.

`tests/test_architecture_boundaries.py` enforces forbidden imports and the Mongo-route/helper boundary, and imports/uses the pure review builder in a fresh process that blocks database/API/provider libraries. Existing characterization, contract, review, projection and import suites test compatibility. A dependency scan alone is not proof that a live route/job has cut over.

## Remaining ownership work

Finish the complete reader/writer/job/mobile/export inventory; production Mongo upload/queue/review authoring integration; the typed patient facade and all downstream readers; reminder consent/timezone/quiet-hour policy and delivery reconciliation; operational observability; and synthetic migration/shadow/rollback rehearsals. The operational Mongo and SQL audit logs are still separate. Protected legacy screens retain comments/tasks/edit capabilities and require the handoff review before migration. Remove code or data only after its actual consumers and retention/hold obligations have been addressed.
